# Security and operations

Use one public HTTPS origin. SvelteKit protects cookie mutations by exact Origin validation and server-side verified Supabase identity; Fastify independently calls Supabase getUser and checks the protected enabled staff row on every staff request. Roles are never accepted from JWT metadata or request bodies. Public signup is disabled in the local Supabase config; disable it on hosted Supabase as well. Keep admin/secret keys out of web containers and out of PUBLIC_* variables.

All business tables have RLS and anon/authenticated privilege revocations in a non-exposed schema. Provision a login role with membership of `babu_runtime` and no superuser/bypassrls privileges. Use that connection for the API and worker. Use a separate privileged connection for migrations, development seed and staff bootstrap. The runtime role must not own the tables. Do not assume RLS substitutes for backend authorization.

Voucher codes use 80 random bits, keyed SHA-256 lookup and an independent AES-256-GCM key. Normal responses expose only the final four characters. Reveal/print/export require permissions, are audited and use no-store. Do not save printed PDFs on shared computers. Browser print/export remains a trusted staff action: no application can prevent an authorized recipient from retaining a copy. CSV fields escape spreadsheet formulas.

Back up all three independently generated 32-byte keys in the deployment secret manager. Losing the encryption key makes reprinting impossible; changing the lookup key without an explicit migration makes existing codes unredeemable. Do not rotate these keys by casually editing .env. Key versioning/online re-encryption is not provided in Phase 1; plan a supervised migration. Never log passwords, bearer tokens, cookies, raw voucher codes or complete portal query strings. API request logs discard query strings; worker errors are generic. Configure reverse-proxy access logs similarly or disable portal query logging.

Configure TRUST_PROXY to specific proxy addresses/CIDRs only. The default trusts no forwarding headers. Public context creation has a high per-IP limit for shared hotspot NAT, with tighter per-context redemption/status limits. This is a bounded Phase 1 control, not a comprehensive anti-bot system. Login throttling is per web process; run one web replica or add an upstream shared limiter before scaling. Portal-origin forgery/MAC spoofing limitations are documented separately.

Back up PostgreSQL (hosted Supabase managed backups plus an independently tested logical backup) and the secret-manager keys. Restore into an isolated project; restore staff auth identities as well as `wifi` tables; verify snapshot integrity and reprinting before cutover. Never restore a stale DB into a network with unexpired controller grants without reconciling the outstanding deadlines first.

Portal contexts expire after 10 minutes and status tokens after 20 minutes; the worker deletes expired token records. Sale idempotency, sales, reversals and audit records are retained; implement business/legal retention policy before production. Avoid collecting optional customer names/phones unless useful. Purging/redacting historical personal data requires a controlled, privileged retention procedure because routine runtime mutation of sale history is blocked.

Disable staff in the Staff screen to revoke application access immediately on the next request, then disable/delete their Supabase auth access as appropriate. Use individual accounts, not shared cashier passwords. Keep at least one enabled administrator; self-demotion is blocked. Bootstrap failures remove the newly created auth user if the profile write fails.

Supabase runtime and migration connections verify TLS using the bundled public Supabase Root 2021 CA, downloaded from https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt. DATABASE_CA_PATH can point to a deployment-specific trusted CA. Hostname verification stays enabled. Review CA changes through the official Supabase dashboard before replacement.
